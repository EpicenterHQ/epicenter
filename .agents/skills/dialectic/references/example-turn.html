Cookie-first is not a preference in this file. It is unconditional.

In requireCookieOrBearerPrincipal, a request that carries a valid session cookie never reaches the line that reads the bearer token. When both credentials arrive naming different principals, the middleware picks one silently and records nothing about the other.

Two credentials naming two principals resolve silently to one. The response gives the caller no sign their bearer token was ignored — a client debugging as principal B sees principal A’s data with a 200.

3 · What the silence means — unresolved

Precedence is the guarantee

Cookie-first is the intended contract. A browser session should win over a token the page happens to carry, and silence is correct.

Ambiguity is the bug

Two principals on one request is a caller error. The boundary should refuse it rather than pick, because picking hides a mistake upstream.

The code is compatible with both readings. Nothing in require-auth.ts, its tests, or its doc comments distinguishes them.

Is preferring the cookie the guarantee, or is a request carrying both a request to refuse?

I would refuse the pair with a 400 naming both credentials, on the assumption that no current client sends both on purpose. If a browser page legitimately calls token-authenticated endpoints while a session cookie rides along, that assumption is wrong and cookie precedence should stand — documented as a guarantee.
