# Push and pull storage costs

Keep automatic folding. These measurements justify investigating update size and
fold scheduling before introducing document replacement for storage maintenance.

## Reproduce

```sh
bun packages/data/src/__benchmarks__/checkout.bench.ts > /tmp/checkout.json
```

[Recorded results](2026-09-09-checkout.json) use `@y/y` 14.0.0-rc.24, Bun 1.3.1,
and the actual `createWorkingCopy` push/pull implementation with an in-memory
SQLite store. The runner checks the installed version. The folder host is an
in-memory HTTP substitute implementing the checkout ETag contract. This is not a
standalone CLI, filesystem, browser, or remote-server benchmark.

Each case starts with one acknowledged row holding a 1 KB, 100 KB, or 1 MB
plain-text body. It performs 100 pulls, unchanged pushes, title edits, or
single-character appends to the body. The unchanged workloads must author no
updates; the runner also verifies the final title or text for edited workloads.

Each workload runs once with new work left unacknowledged, and once with every
operation followed by delivery to an in-memory Yjs receiver, acknowledgement, and
a persistence flush. This models accepted delivery, not server durability or
network latency. The offline case starts with the same acknowledged seed.

`updateBytes` counts authored V2 updates after setup. `foldedBytes` is one
complete encoded state update from the live document. `persisted` counts actual
SQLite update rows and their payload bytes after the store has closed and flushed.
It includes any outstanding work and the tail since the last automatic fold.
It excludes SQLite page overhead. Folder read/write bytes are NDJSON payload
bytes crossing the mocked local host boundary, not remote sync traffic.

## Results for the 1 MB body

Sizes below are decimal MB; the raw JSON contains exact bytes. Every row is
100 operations. These are single-run timings and payload measurements, not a
statistical performance study or a test of peak memory.

| Operation | Authored Yjs bytes | Stored bytes, offline | Stored bytes, acknowledged each time | Fully folded state |
| --- | ---: | ---: | ---: | ---: |
| Pull | 0 | 1.00 MB | 1.00 MB | 1.00 MB |
| Unchanged push | 0 | 1.00 MB | 1.00 MB | 1.00 MB |
| Title edit | about 4.8 KB | 1.003 MB | 1.002 MB | 1.000 MB |
| Append one body character | 100.01 MB | 101.01 MB | 39.00 MB | 1.000 MB |

The body codec replaces the whole text sequence in the existing content node.
That explains why adding 100 characters authors about 100 MB of updates. The
retained CRDT metadata is small in this one-writer workload; the large costs are
repeated payloads in outgoing work and the persisted update tail.

Folding already reduces the acknowledged log. It does not run after every edit:
the current count threshold is 64 foldable updates. At the end of this workload,
39 rows remain, including the folded baseline. A row-count threshold allows a
large byte tail when individual updates are large. Outstanding updates instead
use binary merging, which reduces row count but does not garbage-collect deleted
payloads. A small final snapshot therefore does not establish a small offline
backlog.

There is also local folder I/O overhead independent of CRDT growth. In the 1 MB
case, 100 unchanged pushes read approximately 101 MB of folder payload. The
changing push workflows transfer about 302 MB across the simulated local folder
boundary. Do not attribute those bytes to the remote synchronization protocol.

## What to do next

1. Investigate a byte threshold alongside the count threshold for acknowledged
   log folding. The check must be cheap; it should not read and re-encode the
   entire snapshot after every small edit. Validate large tails, small edits,
   pending dependencies, and acknowledgement races before changing the policy.
2. Prototype smaller updates for changed plain-text bodies. A one-character
   append can be a small sequence edit. General text diffs and rich-content
   codecs need their own correctness tests, including concurrent edits and
   preservation of content structure. Compare generated bytes and offline
   backlog, not just the final snapshot.
3. Measure representative libraries and browser storage before picking budgets.
   These synthetic cases establish where costs arise, not a universal threshold.

Neither removing folding nor replacing the document addresses the primary cost
measured here. Replacement also introduces stale-device retirement. Keep that
mechanism reserved for an explicit restore or demonstrated need to shed causal
history, as described in [ADR-0379](../../adr/0379-reconstruction-is-an-explicit-destructive-library-operation.md).

Validation: the checkout and root-replacement behavior suites pass together
(74 tests). The data package typecheck passes. Production behavior is unchanged.
